# TripGo Trip Service

Лабораторная работа 1: сервис поездок для такси. Три ручки (создать, получить и завершить поездку), плюс /health и /ready. Описание API в contracts/openapi/trip-service.openapi.yaml, данные лежат в PostgreSQL. Сделаны оба задания со звёздочкой: идемпотентность создания поездки и Dockerfile.

## Запуск

Нужны Go 1.26+, Docker, make и tripgoctl.

```
tripgoctl cluster start
tripgoctl environment start
make migrate
make run
```

environment start создаёт файл .env с адресом базы. Пример со всеми переменными лежит в .env.example.

## Переменные окружения

Обязательные, без них (или с пустым значением) сервис не стартует, таймауты должны быть больше нуля:

- HTTP_ADDR - адрес сервера, например :8080
- LOG_LEVEL - debug, info, warn или error
- SHUTDOWN_TIMEOUT - сколько ждать текущие запросы при остановке
- DATABASE_URL - строка подключения к PostgreSQL
- DATABASE_MAX_CONNS, DATABASE_MIN_CONNS - размер пула
- DATABASE_MAX_CONN_LIFETIME - время жизни соединения
- DATABASE_CONNECT_TIMEOUT - таймаут установки каждого соединения с базой, в том числе первого на старте
- DATABASE_QUERY_TIMEOUT - таймаут обращений к базе в рамках одного запроса

Необязательные, это таймауты HTTP-сервера: HTTP_READ_TIMEOUT и HTTP_READ_HEADER_TIMEOUT (5s), HTTP_WRITE_TIMEOUT (10s), HTTP_IDLE_TIMEOUT (60s). Ещё две про идемпотентность: IDEMPOTENCY_KEY_TTL (24h) - сколько живёт ключ, IDEMPOTENCY_PURGE_INTERVAL (1h) - как часто удаляются протухшие ключи.

## Docker

make docker-build собирает образ trip-service из deploy/Dockerfile: многостадийная сборка, итоговый образ на distroless, в нём только бинарь, процесс идёт не от root. Размер итогового образа 25 МБ.

make docker-run запускает его с настройками из .env. Используется --network host, чтобы контейнер видел PostgreSQL из tripgoctl на localhost (проверено на Linux).

## Тесты

make test запускает `go test -race ./...`, в этой работе тестов нет. make lint запускает golangci-lint v2 с конфигом из .golangci.yml, сам линтер нужно поставить отдельно.

## Решения

Уровень изоляции - Read Committed, он стоит в Postgres по умолчанию. Защита от гонок у нас сделана в самой базе (уникальный индекс и условие в UPDATE), так что более строгие уровни ничего бы не дали, только добавили бы ошибки сериализации и повторы. Уровень задаётся явно в Manager.Do.

Менеджер транзакций. Do(ctx, fn) открывает транзакцию, кладёт её в context и вызывает fn. Если fn вернула nil, делается commit, если ошибку или запаниковала, то rollback (паника летит дальше). Репозитории берут исполнителя запросов через ExecutorFrom(ctx, pool): внутри Do это транзакция, вне Do обычный пул, поэтому транзакцию не надо передавать аргументом. Вложенный Do видит транзакцию в контексте и не открывает новую. Rollback идёт на контексте без отмены, чтобы он проходил, даже если клиент уже оборвал запрос.

Запрет двух активных поездок у водителя. В миграции есть частичный уникальный индекс one_active_driver_idx по trips (driver_id) where status = 'active'. Проверка SELECT перед INSERT от гонки не спасает, индекс спасает: второй параллельный INSERT падает с ошибкой 23505, репозиторий превращает её в ErrDriverBusy, а ручка отвечает 409.

Идемпотентность. Ключ из заголовка Idempotency-Key хранится в таблице idempotency_keys вместе с хэшем тела запроса и id поездки. Ключ занимается первым шагом в той же транзакции, что и создание поездки: INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE ключ протух. Поэтому два одновременных запроса с одним ключом дают одну поездку: второй ждёт первого на уникальном индексе и потом получает либо ту же поездку (200, если тело совпало), либо 409 idempotency_conflict. Если создание не удалось (например, driver_busy), транзакция откатывается вместе с ключом, и он не сгорает. Тела сравниваются по хэшу канонического вида, поэтому порядок полей и пробелы не важны. Ключ живёт 24 часа: протухший ключ можно занять заново (это проверяется в том же INSERT, то есть атомарно), а старые строки раз в час удаляет фоновая очистка.

Двойное завершение поездки закрыто условием прямо в запросе: UPDATE trips ... WHERE id = $1 AND status = 'active'. Второй параллельный запрос ждёт блокировку строки и потом не находит подходящих строк. Чтобы отличить 404 от 409, после пустого UPDATE делается дополнительное чтение.
